# LIKELY FIXED 2026-04-13 — Intermittent missed-wakeup in scheduler park/wake

## Status
Likely fixed by commits `4b8eab3` (token), `b48f2b3` (park_while loop).

Confidence is "likely, not proven":
- The shell-dies-after-`ls` symptom was reliably reproducible and is
  no longer reproducing post-fix (10 commands in sequence, multiple
  reboots).
- The original ~1-in-10 boot hang has not reproduced post-fix, but the
  baseline reproduction rate was low enough that a handful of clean
  boots is not statistically conclusive. Need ~30+ clean boots before
  declaring it dead with confidence.
- The fix is structurally correct (token closes the lost-wakeup race
  class at the primitive level; park_while loop closes the contract
  gap exposed by the token), so even if a different hang appears it
  shouldn't be the same root cause.

If a hang DOES reappear, run the dump_threads recipe at the bottom of
this file. The new SYSCALL/WP columns will tell you immediately
whether it's a residual park/wake bug (WP=1 on Parked = primitive
bug) or something else.

## What it was
Two related symptoms with the same root cause:

1. **Boot hang (~1-in-10)**: all four CPUs idle in `Scheduler::run_idle`,
   user threads (terminal, taskbar) Parked with no wake en route. Original
   diagnosis in this file's git history if you need it.
2. **Shell exits after a command**: typing `ls` produces output but no
   new prompt. The shell process exited cleanly with code 0 right after
   spawning the child. `dump_threads` showed the shell tid simply gone.

## Root cause
Two bugs stacked on top of each other:

**Bug A — lost wakeup at the primitive level.** The classic park/wake
race: producer publishes its event state and calls `wake_thread` while
the consumer is between "checked condition, decided to park" and "CASed
state to Parked". The waker observed Running, fell into a 64-PAUSE
retry loop, and silently dropped the wake when the loop expired before
the parker reached Parked. The `wake_thread_from_irq` Running case was
strictly worse — no retry at all, just `mark_need_resched + IPI` and
hope the parker hasn't transitioned yet.

**Bug B — broken contract for `thread_park_while`.** Once the token
landed (Bug A fix), `transition_park_while` could return "no switch"
for two distinct reasons: (a) closure said don't park; (b) stale wake
token was consumed during the transition. The old `thread_park_while`
exited on either, treating both as "condition is satisfied." Callers
without their own retry loop — `sys_waitpid` in particular — saw the
spurious return and proceeded as if the wait had completed.

The shell symptom was Bug B falling through `sys_waitpid` → return 0
without writing `status` → userspace `waitpid` returns -1 → shell's
`run_chain` returns -1, which is its sentinel for "exit shell."

## The fix

### Wake-pending token (kernel/src/thread/{thread,scheduler}.rs)
- New `Thread.wake_pending: AtomicBool`.
- Wakers call `signal_wake()` BEFORE probing state — establishes
  happens-before with the parker's consume.
- `transition_park`, `transition_park_while`, `transition_sleep` call
  `consume_wake_pending()` after CAS to Parked/Sleeping. If true, revert
  state to Running and abort the park/sleep.
- `wake_thread_slow` and `wake_thread_from_irq` collapsed to a single
  `do_wake` function. Retry loop and `MAX_RETRIES` deleted.

### Looping `thread_park_while`
- Re-evaluates the closure after every return from `save_transition_switch`.
- Returns ONLY when the closure observes false. Spurious wakes (token
  consumed without a real condition change) are absorbed by the loop.
- Callers without their own outer loop (`sys_waitpid`) are now correct.

### New state transition
Added `Sleeping -> Running` (sleep abort via consumed token) to
`is_valid_transition`.

### Debug visibility (commit `66f4c68`)
- `Thread.last_syscall: AtomicU32` — single relaxed store at the top of
  `syscall_handler` via the new `with_current_thread` no-clone accessor
  on `PerCpuData`.
- `tools/debug/dump_threads.gdb` gained `SYSCALL` and `WP` columns. For
  any future hang, the dump tells you immediately which syscall each
  parked thread is in and whether its wake token is set.

## How to reason about it now
- Producers MUST call `signal_wake` before any state observation if they
  want a wake delivered. `wake_thread*` does this for you.
- Parkers MUST call `consume_wake_pending` after CAS to Parked/Sleeping
  if they want the token to close the race. The three transition
  functions in scheduler.rs do this.
- `thread_park_while` guarantees: returns only when its closure observes
  false. Callers with no outer loop are correct.
- Bare `thread_park` is "may return spuriously, caller loops." Standard
  `loop { check; park; }` pattern (Rust std::thread::park semantics).

## If a similar hang reappears
Run `tools/debug/dump_threads.gdb` against the running QEMU. New
columns make diagnosis fast:

- `WP=1` on a Parked thread → primitive bug (token set but parker did
  not consume). Should never happen with the current implementation.
- `WP=0` on a Parked thread → producer never called `wake_thread`. That
  is an application/protocol bug, not a scheduler bug.
- `SYSCALL=FUTEX_WAIT|WINDOW_POLL|READ|...` tells you exactly where the
  thread is parked without a backtrace walk.
