## Boot Race / Heap Expansion Bug (fixed)

All fixes implemented:
1. **Lazy vmalloc fault handler** -- page fault handler walks kernel PML4
   lock-free for faults in KERNEL_HEAP..VMALLOC_END. If mapping exists,
   invlpg and retry. Handles stale paging-structure cache entries.
2. **Heap expansion serialization** -- AtomicBool EXPANDING ensures only
   one CPU expands at a time. Waiters spin then retry.
3. **Per-CPU heap freelists** -- 6 size classes (32-1024 bytes), 16 slots
   per CPU. Most small allocations avoid the global heap lock. Batch
   refill/drain of 8 objects. FSGSBASE enabled for fast per-CPU access.
4. **TLB flush fix** -- switch_to_kernel_page() no longer calls
   tlb_flush_all_including_global() unconditionally. Cr3::write
   already flushes non-global entries. The unconditional global flush
   was the root trigger for the intermittent boot hang.
5. **Page fault off IST** -- Page fault handler uses the kernel stack
   instead of IST 1. Nested page faults (vmalloc fault during demand
   fault handling) work naturally. Double fault retains its own IST
   for stack overflow protection.

TLB shootdown IPIs also implemented for safe page unmapping on SMP
(deferred frame free in munmap, shootdown in COW fork).

The 512KB heap warmup workaround was removed. 20/20 boot passes
(was ~1 in 5 failure rate).

## Open questions / loose ends

### Transient boot GPF — ROOT-CAUSED 2026-04-15 (frame allocator aliasing)
Earlier "transient boot GPF" in `IntrusiveList::push_back` with a
non-canonical head/tail was a secondary symptom of a bigger bug:
the physical frame allocator was handing out the same phys frame
twice (heap ↔ vmalloc DMA). virtio-gpu DMA response data was
overwriting scheduler runqueue memory, producing the non-canonical
pointer.

Root cause: `MemoryManager::map_address` / `map_address_range` set
the bitmap bit for the target phys but did not bump the refcount.
`unmap_memory`'s `deallocate_frame` later decremented a refcount
that was never incremented — when the phys was ALSO held by a
heap mapping (refcount=1 from `allocate_frame`), the decrement
took it to 0, cleared the bitmap bit, and the next allocation
returned that still-mapped frame.

Fix: `map_address` now calls `inc_or_set_refcount` instead of
`set_frame_allocated`. Each mapping holds a real refcount; the
final unmap drops to 0 and clears the bit.

Regression guard: `memory::verify_kernel_no_phys_aliasing()` runs
at the end of `init_drivers()` and panics if any kernel-half phys
is mapped at two virts. Also a hard `assert!` in
`BitmapFrameAllocator::deallocate_frame` catches refcount-0 double
free. The intrusive-list canonical-address debug_assert stays as
defense in depth.

### Warm spawn latency regression after inode_cache removal
Removing `EfsDriver::inode_cache` was correct design (one cache,
not two) but warm `/bin/ps` load went from ~0.2ms (pre-block-cache,
BTreeMap hit) to ~6ms (block page cache lookup + inode parse). Not
urgent — 6ms is fine absolutely — but if warm spawn latency
matters later, add a tiny CPU-local inode parse cache (say 8
entries, FIFO) in EFS to avoid re-parsing the same inode on every
open.

### FAT32 full-cluster write vs RMW
Aligned full-page writes now skip RMW. Cluster writes that are
smaller than a page (e.g. 512B sector with cluster_size=1) still
RMW. Fine for FAT32's small-sector case; document or optimize if
cluster_size starts mattering.

### Scheduler balance: parked-thread migration + wake-to-idle (not fixed)
Observed 2026-04-15 via `ps`: 13 kernel+user threads ended up parked
on CPU 3 while CPUs 0/1/2 each had 2 threads. The biased placement
traced to `pick_sched()`: sorted-lapic iteration + `>=` tie-break made
CPU 3 (last iterated) effectively never win ties, so early boot spawns
that all saw `thread_count=0` initially packed onto one CPU via a
different cascade. Fixed 2026-04-15 by switching `pick_sched` to a
rotating tie-break (`PICK_SCHED_ROTATION: AtomicU32` bumps each call),
so new spawns with equal counts round-robin across CPUs.

Not fixed: existing parked threads stay on their original CPU forever.
Work-stealing only moves Ready/Running. A driver kthread that parks on
CPU X stays on CPU X, gets enqueued back to CPU X's rq on wake. Two
follow-ups worth doing when scheduler load-balancing matters:

1. Let work-stealing steal parked threads too, OR a periodic rebalance
   pass that migrates parked threads from overloaded CPUs.
2. Wake-to-idle hint: when `wake_thread_handle` fires and the target
   thread's home CPU is loaded AND another CPU is idle, redirect the
   wake to the idle CPU's rq. Cleaner to do post-Foundation-#1 since
   the wake path already takes a `Weak<Thread>` handle.

### Driver kthread startup starvation on busy CPU
Observed 2026-04-15: mouse kthread can take up to 5 seconds to
start running because `pick_sched()` at spawn time placed it on the
same CPU as the e1000e driver kthread, which was blocked on DHCP
for ~5 seconds. Meanwhile `edos-wm` spawned by `system-mount` at
~1.5s tried `open("/dev/mouse")`, got `InvalidInput` (device not
yet registered in devfs), panicked, and exited. No automatic retry.

Two issues conflate here:
1. Scheduler places cooperative-blocked-driver kthreads and
   latency-sensitive driver kthreads on the same CPU, starving the
   latter until the former unblocks.
2. Userspace programs assume their required `/dev/*` entries exist
   at program start. They don't (drivers register async).

Fix options, ranked:
- (best) `system-mount` should wait for `/dev/mouse` and `/dev/kbd`
  to exist before spawning `edos-wm` (and any program that depends
  on input). Possibly a generic "wait for device" syscall or a
  `/dev/.ready` sentinel.
- edos-wm retries `open("/dev/mouse")` with backoff instead of
  panicking on first failure.
- `queue_spawn_kthread_named_on(cpu)` variant so mouse and keyboard
  go to specifically different CPUs from network drivers.
- Convert DHCP wait from `thread_park_while` on a 5s hard timeout
  to an event-driven kthread that yields between short polls.

## Ideas

### Foundations for async I/O (TOP PRIORITY, unblocks multiple features)

Discovered while planning async NCQ readahead
(`.claude/plans/async-ncq-readahead.md`): AHCI already supports
concurrent NCQ slots and IRQ-driven wake, but a split `submit/wait` API
is unsafe today because of generic kernel-infrastructure gaps. These
aren't "async is hard" issues — they are missing foundations that also
affect other planned work (proper SIGKILL delivery, process-level
cleanup on exec, multi-threaded file I/O, virtio-blk / USB async reads,
reaper correctness in general). Roadmap in dependency order:

1. **Thread handles with Arc / Weak refcounting instead of raw TIDs.**
   **DONE 2026-04-16.** `Scheduler::wake_thread` / `wake_thread_irq`
   now take `&Weak<Thread>` exclusively; the TID-based API is deleted.
   Every sync primitive (WaitQueue, PollWaiter, Subscriber, AHCI
   slot_waiters, ThreadExitRegistry waiters, every driver dispatcher
   thread handle, REAPER_HANDLE, kill_process) stores `Weak<Thread>`.
   A dangling Weak upgrades to `None` → `wake_thread*` is a silent
   no-op instead of waking a recycled TID's successor. See CLAUDE.md
   "Thread handles" invariant and `.claude/plans/arc-weak-thread-handles.md`.

2. **Cancellable / transferable waits for dying threads.** When a
   thread is killed (SIGKILL, process group termination) while parked
   on I/O, the reaper needs a way to hand off ownership of the
   pending resource (kernel cleanup thread, destination page cache).
   Today the reaper just drops the stack, so anything with a blocking
   Drop deadlocks the reaper. Pieces: a "cleanup queue" the reaper
   drains, `Drop` contracts that never block, per-thread list of
   owned async resources. Prereq for real signal handling too.

   `CachedPage::drop` deallocates the frame on last Arc drop (mirrors
   `CachedBlockPage::drop`). Removed the manual `deallocate_frame` in
   `InodePages::get_or_fill`'s race-insert path and the
   `strong_count == 1` heuristic in `invalidate_from`. Debug assert on
   `pin_count == 0` at drop caught a pre-existing pin leak in
   `store_cached_page_on_vma` (fixed: unpin at entry).

4. **Strict lock-order discipline for fs/page-cache paths.**
   **DONE 2026-04-17.** Canonical rank table in
   `doc/invariants/lock-order.md` (ranks 10-200 for subsystem locks;
   900/910 for deep utility leaves kernel_mapper/frame_alloc).
   Per-thread rank stack (`Thread.lock_ranks`, `heapless::Vec`, debug
   only) enforced by `ranked_lock!` / `ranked_read!` / `ranked_write!`
   macros and `RankedGuard<G>` (ManuallyDrop-based RAII). All ~80
   ranked lock sites across VFS, page-cache, journal, EFS, AHCI, frame
   allocator, and memory manager instrumented. `/proc/lock_order_stats`
   exposes inversion count + max stack depth. `lockordertest` program
   verifies inversions==0 after a representative workload.

   **Caught 6 pre-existing latent lock-order bugs in one session:**
   (1) journal `tracker->state` AB/BA via `committed_seq()` under
       `checkpoint_tracker` in `is_safe_to_flush`/`advance_tail`;
   (2) thread-teardown `mm(80)->vmas(70)` in TLS cleanup + last-thread
       VMA teardown, narrowed by drop-reacquire;
   (3) EFS `mutable(160)->BPC(110)` in `alloc_inode`/`alloc_block`,
       fixed by adding `alloc_mutex(32)` serializer and narrowing
       `mutable` scope out of BPC I/O (**side-effect perf win**:
       mmaptest full suite dropped to ~200ms — mutable no longer held
       across AHCI reads);
   (4) BPC `shard(110)->frame_alloc(90)` via `CachedBlockPage::drop`
       during eviction, fixed by deferring Arc drops out of shard scope;
   (5) VFS `inode(30)->VFS(10)` in `list_files` calling

       translation during writeback — fixed by moving kernel_mapper
       and frame_alloc to deep-leaf ranks (900/910). **Systemic
       lesson**: utility leaves called from arbitrary contexts must be
       numerically HIGHEST in the rank table, not near their
       call-site neighbors.

   Each rank-fix was also a lock-hold-time shrink (overbroad locks
   get caught because they're held across paths that reach lower
   ranks). The tracker doubles as a "lock-hold-time linter". See
   `.claude/plans/foundation-4-lock-order.md` and the session handoff
   at `.claude/handoff/2026-04-17-2-foundation-4-complete.md`.

Residual from #6: `enter_ncq_mode` does not gate on
`AhciPort.restarting`, so a submitter can install a fresh `AhciNcqOp`
around the time a port reset runs.

Traced 2026-08-08, and it is milder than the watchdog module comment
implies. The existing generation machinery already self-heals it:
`fail_all_ncq_slots` deliberately skips ops with `issued == false`, and
the submitter's post-issue SACT self-check then observes the cleared
bit, calls `complete_ncq_slot`, and fails the op on the
`cur_gen != op.start_gen` mismatch. So an op caught mid-reset is failed
promptly rather than left pending.

The genuine residual is narrower: an op that is already `issued` with
SACT still set when the reset finishes waits for the next watchdog
sweep, costing up to 30s of latency. That is a latency bug, not a lost
I/O, so gating `enter_ncq_mode` on `restarting` (and waking
`mode_waitq` when it clears) is a robustness improvement rather than a
correctness fix. Worth doing, but it touches the submit path of the
storage stack, so it should land with runtime validation rather than on
inspection alone.

### Extend lock-order ranks to more subsystems (Foundation #4 follow-up)

Foundation #4 shipped rank instrumentation across VFS, page-cache,
journal, EFS, AHCI, frame allocator, and memory manager. The mechanism
(`ranked_lock!` + `Thread.lock_ranks` + per-thread rank stack) is
generic and applies to any `Mutex`/`RwLock`/`IrqSpinlock` in the
kernel. In the fs/mm audit it caught 3 real pre-existing inversions in
its first boot cycle (journal `tracker->state`, thread teardown
`mm->vmas`, EFS `mutable->BPC`). Extending to other subsystems is a
high-ROI way to shake out latent inversions before they manifest as
rare concurrent-load hangs. Candidates, ranked by fun-per-effort:

1. **Networking stack** — TCP state machine, socket tables, route
   table, ARP cache, e1000e/virtio-net driver locks. TCP nested
   locking (socket lock -> send queue -> retransmit timer) is a
   classic inversion trap. Probably the highest payoff.
2. **USB stack** — xHCI ring locks, device enumeration, HID dispatch.
   Foundation #2 drop-audit already noted async `block_api`
   interactions worth verifying.
3. **Window system** — window registry, focus, input routing, shared
   memory compositor. Multi-threaded (client + compositor + input
   threads), ripe for latent inversions. User-facing so inversions
   manifest as WM hangs.
4. **HDA audio** — codec/stream/buffer locks. Currently marked "out
   of Phase 2 scope" in `doc/invariants/lock-order.md`.
5. **devfs / PTY** — `tty_lock -> line_discipline -> char_device`
   kind of chains.

Marginal cost per subsystem: one rank constant, one row in
`doc/invariants/lock-order.md`, and s/`.lock()`/`.lock_ranked(RANK,
"site")`/ on ~10-30 sites. Per-subsystem cost a few hours; expected
payoff is a real bug or two per subsystem based on fs audit yield.

### Guards held across kill points leak (TOP PRIORITY, 2026-08-08)

Found by an agent-driven soak: ~630s of continuous synthetic input via
`scripts/edos-vm` deadlocks the whole GUI. All four CPUs end up
spinning in `spin::RwLock<WindowRegistry>::write`. The lock word reads
`0x4`, which is one outstanding *reader* and no writer, so it is a
leaked read guard, not a lock cycle.

`sys_window_list` holds `WINDOW_REGISTRY.read()` across
`try_copy_to_user` (`syscalls/window.rs:315` to `:356`). EDOS is
`no_std` with no unwinding, so a thread killed during that copy never
runs `RwLockReadGuard::drop` and the reader count is never decremented.
`edos-wm` calls this every frame, so the window is hit constantly.

Full writeup: `doc/bugs/2026-08-08-window-registry-reader-leak.md`.

The narrow fix is to build entries into an owned Vec, drop the guard,
then copy out. The general problem is bigger and worth treating as its
own workstream:

- Audit every lock guard that is live across `try_copy_to_user`,
  `copy_from_user`, a demand fault, or a park. Each one is a permanent
  leak the first time its holder is killed there.
- Consider whether the reaper can do anything about guards at all.
  Today it frees the stack and destructors never run. A per-thread list
  of held ranked locks (`Thread.lock_ranks` already exists in debug
  builds) could at least *detect* a thread dying with locks held.
- This is the sibling of the drop contract: that one says drops must
  not block, this one says guards must not be live where a thread can
  die.

### Userspace allocator fragments without bound (FIXED, edos_rt 0.0.36)

Presents as "edos-wm leaks heap": on a fully idle desktop the WM grows
its heap by 64 KiB every 9.2 seconds, metronomically, and never gives
any back. 24 consecutive growths at 9.18-9.30s spacing during a window
with no input and no process churn, zero munmaps in the whole log.

It is not a WM bug. The 64 KiB matches `CHUNK_SIZE` in `edos_rt`'s
`PoolAllocator`, and that allocator has three compounding defects:

1. **No coalescing.** `add_to_free_list` pushes blocks onto a singly
   linked list and `split` carves them up, but adjacent free blocks are
   never merged. Under a steady alloc/free workload the list shatters
   into fragments that individually satisfy nothing, so
   `allocate_new_chunk` grabs another 64 KiB. Growth is therefore
   proportional to allocation *rate*, not to retention, which is why the
   period is so exact.
2. **Sub-16-byte blocks are dropped.** `add_to_free_list` returns early
   when `size < size_of::<FreeBlock>()`, permanently losing the block.
3. **The tail of an exactly-fitting block is lost.** When `split` takes
   the "use entire block" branch it hands out a block larger than
   requested, but `dealloc` records `total_size` as the *requested*
   size, so the excess never returns to the list.

Any long-running program is affected; the WM is merely the busiest
allocator. It is the same reason the VA cursor advanced ~940 MB per
9.2s: every chunk was a fresh mapping.

**The fix was not a change to this repo.** `edos_rt` is a separate crate
published to crates.io and consumed through the Rust fork, so the loop
was: patch, bump, publish, update `library/std/Cargo.toml` in the fork,
rebuild the toolchain, rebuild programs.

Fixed in `edos_rt` 0.0.36. The free list is address-ordered and a
returned block absorbs whichever neighbours it touches; a merge cannot
join two chunks, because each chunk's usable region is preceded by the
chunk header inside the same mapping. Spans are rounded up to a
`FreeBlock` and to 8 bytes, so nothing untrackable is produced and
adjacent spans touch exactly. Chunks reserve the exact span and the
header records that span, so padding and tails come back on free.

Fragmentation also made allocation quadratic, since first fit walked an
ever-growing list. `bench/allocstress` in the `edos_rt` repo compiles the
allocator against a shimmed `mmap` on the host and asserts the pool
plateaus: a 200-allocation working set that mapped 22 MB in 41s over 200k
cycles now holds a flat 128 KiB in 21ms, unchanged at 2M cycles.

The std fork pin was ten releases behind (0.0.26), so this also brought
`msync`, file-backed `mmap` and the `OpenFlags` access-mode constants
into std for the first time.

### User virtual address space is never reused (2026-08-08)

`VmaSet::find_free_address` (`memory/vma.rs:247`) is a monotonic
`hint.fetch_add(aligned_length)` bump allocator. Freed VA is never
returned to the pool, so address space is consumed linearly with
allocation *count*, independent of how much is live.

Measured on an idle desktop: ~940 MB of user VA consumed per 9.2s,
39.6 GiB over ten minutes, against only 2.4 MiB of live mappings. That
is roughly a 15,000x amplification, and it exhausts the 128 TiB user
half in about two weeks of uptime. The stride is far larger than the
64 KiB being mapped because the compositor's per-frame mappings bump
the same shared hint between the WM's heap growths.

Fix direction: track free ranges properly (the VMA tree already has
the information), or at minimum reset the hint when the address space
is empty and reuse holes below it.

### Async NCQ pipelined readahead (Foundations now shipped)

Linux's async-marker readahead: when the user reads the last page of
the current window, the kernel pre-fires the NEXT window's I/O so it
completes while the user consumes the current batch, keeping the I/O
pipeline full. Current EDOS readahead is sync-only, so steady-state
64 KiB user reads still trigger 64 KiB AHCI commands — the prefetch
window follows the user rather than pulling ahead. Small-file whole-
file prefetch (shipped 2026-04-15) covers files ≤ 2 MiB; async is
needed for the large-file case.

The Foundations this was blocked on are all shipped, and Phase C2
(`83ddde9`) landed async readahead via lazy finalization by the first
joiner. What remains is the pipelined async-marker behaviour proper:
firing the *next* window's I/O when the user reads the last page of the
current one, so the prefetch pulls ahead instead of following.

Payoff once Foundations + this land: first-run mmaptest test 10 on
/var EFS drops from ~500 ms (current, with whole-file prefetch) to
~150 ms; concurrent-read throughput improves across the board;
writeback/read overlap becomes possible.

### EFS write-path perf: batch journal tx per flush_dirty round (DONE 2026-04-15)
Shipped as commit `824e656`. Added `PageCacheOps::flush_pages_bulk`
with a default per-page loop; EFS overrides to chunk pages in 512-page
batches, each with one TxHandle and one `ensure_blocks_for_logical_batch`
(read inode once, walk all logical blocks with extent coalescing, write
inode once). Direct AHCI page writes bypass BlockPageCache. Also added
`InodePages::flush_dirty_bulk` with all-or-nothing semantics. vfs
`flush_file` and `flush_dirty_inodes` migrated. mmaptest test 7
(fsync+msync) on /var EFS: ~4.1s → 159ms (26x).

### EFS write-path perf: sequential-extent pre-allocation (up next after batching)
`flush_page` currently allocates one cluster at a time via
`ensure_block_for_logical`, which walks the extent tree per call and
splits what could have been one contiguous extent into many tiny
ones. For a growing file, we should detect the "append pattern" and
pre-allocate a contiguous extent of N blocks up front (maybe 32 or
64), then let subsequent `flush_page` calls land inside the already-
allocated range without walking/appending the extent tree. This
matches ext4's delayed allocation + multi-block allocator (mballoc).
Payoffs: fewer extent-tree entries on disk (less metadata to flush),
fewer bitmap updates (one BGD transaction per big alloc, not 480),
contiguous data on disk (faster reads later).

### PageCacheOps for FAT32 + memfs
Today only EFS implements PageCacheOps, so file-backed mmap (and the
new FileBacked ELF loader) returns EINVAL/ENOEXEC on FAT32 and memfs.
Binaries copied to a USB FAT32 drive cannot exec, and mmap'ing files on
/tmp falls back to read+anon. Wiring PageCacheOps through both drivers
unblocks both paths.

### Dynamic Linker (ld.so)
ELF dynamic linking: PT_INTERP, PT_DYNAMIC parsing, symbol resolution
(DT_HASH/DT_GNU_HASH), PLT/GOT lazy binding, dlopen/dlsym/dlclose.
Requires General Dynamic TLS model + DTV (dynamic thread vector).
Shared libraries share physical pages across processes via MAP_SHARED
file-backed mmap. Enables C library use, plugin systems, and shared
memory savings. Natural ordering: page cache -> file-backed mmap ->
dynamic linker.

### io_uring-style Async I/O
Shared-memory submission/completion ring between userspace and kernel.
Already have the SHM infrastructure. Very "modern OS" feature, unique among hobby OSes.

### IPv6
Full IPv6 support: different header format, NDP (replaces ARP), ICMPv6,
SLAAC/DHCPv6 for address configuration, multicast. Source-only fragmentation
(different model from IPv4). Not urgent since most targets work fine on v4,
but needed for a complete real-hardware network stack.

### GPU driver work (far future, no near-term plan)

The virtio-gpu driver we have is 2D only: dirty-rect transfers, blob
resources, hardware cursor. Two directions exist, and they teach
opposite halves of what a real GPU driver is. Neither is scheduled;
this is here so the options are written down rather than rediscovered.

**`ati-vga`, the hardware-facing half.** QEMU emulates a real ATI Rage
128 Pro / Radeon 9250 (`-device ati-vga,model=...`), with real MMIO
registers, a real 2D engine and a hardware cursor. The r100/r200
register documentation is public; it is what the classic `radeon` DRM
driver was built from. Bring-up would be authentic: PCI BAR probing,
MMIO programming, VRAM aperture setup, engine init, 2D blits, DMA.

The advantage over real silicon is that the device model *is* the spec.
`hw/display/ati.c` and `ati_2d.c` in the QEMU tree say exactly which
registers are implemented and what each does, so a hang is diffed
against the model rather than guessed at, and a `printf` can be added to
the model itself. The catch: it is hardware from 2003. No shaders, no
command processor, no GPU MMU.

**virtio-gpu 3D, the API-facing half.** Extending our existing
virtio-gpu driver past 2D means contexts, resource create/attach,
command-stream submission and fences, which is genuinely the object
model every modern DRM driver uses, and it builds on code we already
have.

Target the modern capsets rather than virgl. **Venus** (Vulkan) and
**native contexts** run a real Mesa driver in the guest and forward
actual hardware ioctls over the transport, so the guest side is doing
what a real driver does. Virgl is the older path: its command stream is
essentially serialised GL calls the host translates, which is further
from hardware and is not where the ecosystem went. QEMU exposes 3D
through the `-gl` device variants (`virtio-gpu-gl`, `virtio-vga-gl`),
which are compiled into the QEMU we run; the capset chosen on top of
that is what decides whether this is virgl or venus.

What the virtio path does *not* teach, and this is most of the
difficulty in a real driver: shader compilation to a hardware ISA, the
GPU's own MMU and page tables, firmware loading, engine scheduling and
preemption, clock and power management, and the VRAM/GTT hierarchy with
migration and eviction. Those live on the `ati-vga` side of the fence,
or on real silicon.

**Passthrough is not currently an option on the dev box.** VFIO would
need IOMMU enabled in firmware and on the kernel cmdline
(`/sys/kernel/iommu_groups` is empty today), and the only GPU is a
GeForce GT 710 driving the host display. A from-scratch Kepler driver
also means signed firmware for several engines; nouveau still cannot
reclock Kepler properly.

### virtio-net
Second NIC backend. Straightforward now that the stack and e1000e exist.
Useful for VMs where e1000e emulation is slower than paravirtual.

### In-EDOS fsck (`/bin/fsck`)
Host `efs-fsck` is the canonical recovery tool. A thinner in-EDOS
userspace wrapper would be useful for unmounted secondary block
devices (USB drives, second SATA, attached image files). Cannot fsck
the live root FS without an initramfs (chicken-and-egg), and EDOS has
none — kernel still replays journal automatically on mount, which
covers the common boot case. Code reuse: `libs/efs-common` is already
`no_std` and works in userspace; the host crate's `std::fs::File`
calls would swap for `open("/dev/sdb")` + `pread`/`pwrite`/`fsync`.

**Prereq investigation**: check `kernel/src/fs/devfs/` to see what
`/dev/sda` exposes today. Raw block-device-as-file (open+pread on a
sector-aligned device node) may not be wired. If it isn't, that's the
first piece to land before any in-EDOS fsck makes sense.

### Addressing windows by name instead of by pixel

`scripts/edos-vm` drives the GUI by clicking absolute pixels, and its
taskbar coordinates are a hand-copied mirror of the constants in
`programs/edos-taskbar/src/main.rs` (`LAUNCHER_X`, `LAUNCHER_WIDTH`,
`BUTTON_WIDTH`, `TASKBAR_HEIGHT`). Any GUI layout change silently
breaks every scripted click, with no compile error and no failing test
-- the click just lands on the wrong button.

Two ways out, cheap to expensive:

1. **Expose the window registry through procfs.** `kernel/src/window/
   registry.rs` already holds id, pid, rect, z-order and title, and
   `SYS_WINDOW_LIST` (224) already returns it to userspace. A
   `/proc/windows` line per window costs little and makes layout
   introspectable. Still needs a channel out of the guest to help an
   external driver.
2. **A control daemon (the `edosd`/rcon idea above), speaking window
   names.** `focus Terminal`, `launch term`, `click <window> <dx> <dy>`
   resolved guest-side against the live registry. Pixels stop being the
   interface, so GUI layout changes stop breaking automation, and
   assertions can read text instead of screenshots.

Until then, the mirrored constants are documented in
`doc/vm-control.md` and must be updated in the same commit that moves
the taskbar layout.

## What to do next (reviewed 2026-08-08)

Shipped this session, all verified on hardware unless noted:

- **User VA is reused.** `find_free_address` is a first fit over the VMA
  tree searching from the base every time. Mapping stride fell from
  ~940 MB to 8-10 MB, and successive mmap/munmap cycles return the same
  address.
- **`sys_window_list` no longer holds a spin guard across a user copy.**
  3000 soak rounds and 207k registry acquisitions with no stuck reader.
- **Filesystem errors keep their errno** instead of being flattened to
  EINVAL; missing paths report ENOENT.
- **`make filesystem` creates the directories it claims to.** It relied
  on brace expansion, which dash does not do, so `/var` never existed.
- **`OpenOptions` actually opens files for writing.** `read`, `write`,
  `truncate` and `create_new` were no-op stubs in the std fork, so every
  file opened read-only as far as the kernel was concerned. mmaptest went
  from failing at test 3 to all 10 passing on `/var` and `/tmp`.
- `sha256sum` and `file` (Phase 3 userspace).

- **The window-registry hang is root-caused and fixed.** The holder was
  never parked; it was Ready and starved. The scheduler armed a
  timeslice it never enforced, and its anti-starvation path only
  covered wake-boosted threads, so a priority-10 kthread spinning on a
  lock held by a priority-7 thread deadlocked outright. Both fixed,
  with `starvation-victim` in sched_test as the regression test. This
  bounded every spin lock in the kernel, not just the window registry.
- **`make test` is green (31/31)**, having been red on trunk: the
  abort-race test was a bare `thread_park_while` caller.
- **Spin locks shared between threads now suppress preemption**
  (`thread/preempt.rs`: per-CPU counter honoured by `maybe_preempt`,
  plus PreemptSpinlock/PreemptRwLock). Converted VFS, vmas,
  memory_manager, shared memory, the thread registries and the window
  locks. Preemption rather than interrupts, because vmas and mm are
  held across tree and page-table walks. The park primitives
  debug-assert preemption is enabled, which audits the whole class.
- **VfsInode::drop no longer panics on the reaper.** The drop-contract
  guard asserted "never runs here" when the contract is "never blocks",
  and the reaper releasing an orphaned inode is exactly the case the
  evict kthread exists for. mmaptest's unlink-while-mapped test
  panicked the kernel on trunk; now 10/10 on /var and /tmp.

- **The userspace allocator no longer fragments without bound.** The WM's
  metronomic 64 KiB-per-9.2s heap growth was `edos_rt`'s `PoolAllocator`
  never coalescing. Fixed in 0.0.36 (details above), which also carried
  the std fork's pin forward ten releases from 0.0.26.
- **`edos_rt` 0.0.37: the rest of the runtime.** Reading the crate after
  the allocator fix turned up more than the fragmentation did. The
  syscall wrappers were `no_mangle extern "C"`, so every syscall paid an
  out-of-line call plus a shuffle from the C argument registers into the
  kernel's, and the exported symbols were what forced `edos_lib` and four
  programs to hand-roll their own copies; they are inline Rust functions
  now, which is sound because the kernel's entry stub restores every
  argument register. `thread_join` asked for a non-blocking `waitpid` and
  slept 1 ms in a loop, so every `JoinHandle::join` polled at 1 kHz.
  `getrandom` returned a count that std's `fill_bytes` discarded, so a
  short read left the tail of the buffer holding whatever was there
  before. `IoError` folded every errno but three into `Unknown`, which is
  why errors displayed as "uncategorized" no matter what
  `decode_error_kind` mapped. The allocator now unmaps idle chunks
  instead of only plateauing, honours alignment above a page on large
  allocations (`mmap` alone returned them 4 KiB out), caches freed large
  mappings within a 4 MiB bound, and uses the futex mutex rather than a
  spin lock that a preempted holder turned into the userspace version of
  the kernel starvation bug.

Open, roughly in priority order:

1. **AHCI watchdog `restarting` gate.** Latency only, needs runtime
   validation on the storage path.
2. **`decode_error_kind` in the std fork maps only five errnos**, so
   everything else displays as "uncategorized error".

Then, by fun-per-effort:

more tools > dynamic linker > PageCacheOps for FAT32+memfs > in-EDOS
fsck > IPv6 > virtio-net

Far future, deliberately unscheduled: GPU driver work (see above).

Storage-roadmap steps 1-4 are shipped (host fsck done). File-backed
mmap, ElfSegment->FileBacked loader migration, lazy ELF relocation, and
the whole async block I/O foundations chain (#1-#6) are shipped. The
next step in the memory/loader progression toward the dynamic linker is
