# EDOS ideas

Design notes and loose ends that are not tasks: options written down so they are
not rediscovered, and post-mortems whose mechanism is worth keeping.

**Pending work is not here.** It lives in engram -- `engram-cli todo list` --
which is the single place to look for what is open. Shipped work and its
mechanism moved to `SHIPPED.md`.


## Storage Stack Roadmap

Starting point: system-mount kthread wall=1379ms, cpu=326ms (~1s of
I/O stall). Three create_dir calls for /dev, /proc, /tmp cost ~720ms.

Steps 1-3 are done (see `SHIPPED.md`). Current system-mount wall:
~808ms. FS IS crash-safe for metadata (journal replays on mount).

### 4. fsck tool (DONE — host)

Host tool `tools/efs-fsck/` shipped. Scans inodes, verifies bitmaps,
reclaims leaked blocks, replays journal if mounted dirty. Read-only by
default; `--repair` opts into destructive fixes with per-class prompts
(`-y` to auto-accept). Linux-style exit codes (0/1/4/8/16). Shares the
journal parsers with the kernel via `libs/efs-common/journal_parse.rs`
(only kernel change in the whole feature). `fsck_in_progress` sentinel
byte stolen from superblock reserved area so a killed-mid-repair fsck
refuses to re-run without `--force`. 8 integration tests + doc at
`doc/efs-fsck.md`.

## Open questions / loose ends

### Transient boot GPF — ROOT-CAUSED 2026-04-15 (frame allocator aliasing)
Earlier "transient boot GPF" in `IntrusiveList::push_back` with a
non-canonical head/tail was a secondary symptom of a bigger bug:
the physical frame allocator was handing out the same phys frame
twice (heap ↔ vmalloc DMA). virtio-gpu DMA response data was
overwriting scheduler runqueue memory, producing the non-canonical
pointer.

Root cause: `MemoryManager::map_address` / `map_address_range` set
the bitmap bit for the target phys but did not bump the refcount.
`unmap_memory`'s `deallocate_frame` later decremented a refcount
that was never incremented — when the phys was ALSO held by a
heap mapping (refcount=1 from `allocate_frame`), the decrement
took it to 0, cleared the bitmap bit, and the next allocation
returned that still-mapped frame.

Fix: `map_address` now calls `inc_or_set_refcount` instead of
`set_frame_allocated`. Each mapping holds a real refcount; the
final unmap drops to 0 and clears the bit.

Regression guard: `memory::verify_kernel_no_phys_aliasing()` runs
at the end of `init_drivers()` and panics if any kernel-half phys
is mapped at two virts. Also a hard `assert!` in
`BitmapFrameAllocator::deallocate_frame` catches refcount-0 double
free. The intrusive-list canonical-address debug_assert stays as
defense in depth.

### FAT32 full-cluster write vs RMW
Aligned full-page writes now skip RMW. Cluster writes that are
smaller than a page (e.g. 512B sector with cluster_size=1) still
RMW. Fine for FAT32's small-sector case; document or optimize if
cluster_size starts mattering.

## Ideas

### Foundations for async I/O (TOP PRIORITY, unblocks multiple features)

Discovered while planning async NCQ readahead
(`.claude/plans/async-ncq-readahead.md`): AHCI already supports
concurrent NCQ slots and IRQ-driven wake, but a split `submit/wait` API
is unsafe today because of generic kernel-infrastructure gaps. These
aren't "async is hard" issues — they are missing foundations that also
affect other planned work (proper SIGKILL delivery, process-level
cleanup on exec, multi-threaded file I/O, virtio-blk / USB async reads,
reaper correctness in general). Roadmap in dependency order:

1. **Thread handles with Arc / Weak refcounting instead of raw TIDs.**
   **DONE 2026-04-16.** `Scheduler::wake_thread` / `wake_thread_irq`
   now take `&Weak<Thread>` exclusively; the TID-based API is deleted.
   Every sync primitive (WaitQueue, PollWaiter, Subscriber, AHCI
   slot_waiters, ThreadExitRegistry waiters, every driver dispatcher
   thread handle, REAPER_HANDLE, kill_process) stores `Weak<Thread>`.
   A dangling Weak upgrades to `None` → `wake_thread*` is a silent
   no-op instead of waking a recycled TID's successor. See CLAUDE.md
   "Thread handles" invariant and `.claude/plans/arc-weak-thread-handles.md`.

2. **Cancellable / transferable waits for dying threads.** When a
   thread is killed (SIGKILL, process group termination) while parked
   on I/O, the reaper needs a way to hand off ownership of the
   pending resource (kernel cleanup thread, destination page cache).
   Today the reaper just drops the stack, so anything with a blocking
   Drop deadlocks the reaper. Pieces: a "cleanup queue" the reaper
   drains, `Drop` contracts that never block, per-thread list of
   owned async resources. Prereq for real signal handling too.

3. **Physical frame RAII for cache pages.** **DONE 2026-04-17.**
   `CachedPage::drop` deallocates the frame on last Arc drop (mirrors
   `CachedBlockPage::drop`). Removed the manual `deallocate_frame` in
   `InodePages::get_or_fill`'s race-insert path and the
   `strong_count == 1` heuristic in `invalidate_from`. Debug assert on
   `pin_count == 0` at drop caught a pre-existing pin leak in
   `store_cached_page_on_vma` (fixed: unpin at entry).

4. **Strict lock-order discipline for fs/page-cache paths.**
   **DONE 2026-04-17.** Canonical rank table in
   `doc/invariants/lock-order.md` (ranks 10-200 for subsystem locks;
   900/910 for deep utility leaves kernel_mapper/frame_alloc).
   Per-thread rank stack (`Thread.lock_ranks`, `heapless::Vec`, debug
   only) enforced by `ranked_lock!` / `ranked_read!` / `ranked_write!`
   macros and `RankedGuard<G>` (ManuallyDrop-based RAII). All ~80
   ranked lock sites across VFS, page-cache, journal, EFS, AHCI, frame
   allocator, and memory manager instrumented. `/proc/lock_order_stats`
   exposes inversion count + max stack depth. `lockordertest` program
   verifies inversions==0 after a representative workload.

   **Caught 6 pre-existing latent lock-order bugs in one session:**
   (1) journal `tracker->state` AB/BA via `committed_seq()` under
       `checkpoint_tracker` in `is_safe_to_flush`/`advance_tail`;
   (2) thread-teardown `mm(80)->vmas(70)` in TLS cleanup + last-thread
       VMA teardown, narrowed by drop-reacquire;
   (3) EFS `mutable(160)->BPC(110)` in `alloc_inode`/`alloc_block`,
       fixed by adding `alloc_mutex(32)` serializer and narrowing
       `mutable` scope out of BPC I/O (**side-effect perf win**:
       mmaptest full suite dropped to ~200ms — mutable no longer held
       across AHCI reads);
   (4) BPC `shard(110)->frame_alloc(90)` via `CachedBlockPage::drop`
       during eviction, fixed by deferring Arc drops out of shard scope;
   (5) VFS `inode(30)->VFS(10)` in `list_files` calling
       `child_mount_points` under inode guard, narrowed guard to the
       FS driver call;
   (6) BPC `write_lock(140)->kernel_mapper(85)` via AHCI DMA
       translation during writeback — fixed by moving kernel_mapper
       and frame_alloc to deep-leaf ranks (900/910). **Systemic
       lesson**: utility leaves called from arbitrary contexts must be
       numerically HIGHEST in the rank table, not near their
       call-site neighbors.

   Each rank-fix was also a lock-hold-time shrink (overbroad locks
   get caught because they're held across paths that reach lower
   ranks). The tracker doubles as a "lock-hold-time linter". See
   `.claude/plans/foundation-4-lock-order.md` and the session handoff
   at `.claude/handoff/2026-04-17-2-foundation-4-complete.md`.

5. **Per-inode async I/O registry (last layer, uses #1-#4).**
   **DONE 2026-04-17.** `InodePages.in_flight` at rank 42 +
   `PageFillHandle` (`fs/page_fill.rs`) + `get_or_fill_async_sync` /
   `get_or_fill_bulk_async_sync` reader state machine + `/proc/inflight_stats`
   + `programs/inflighttest`. Replaces the legacy synchronous
   `InodePages::get_or_fill` (deleted). Publish-terminal-state-before-remove
   invariant enforced in the free fn; handle registered as a per-thread
   `owned_op` so reaper cancels dying-issuer fills. See
   `doc/bugs/2026-04-17-foundation-5.md` and
   `.claude/handoff/2026-04-17-3-foundation-5-phase-4-plus-ahci-ncq-hang.md`.

3. **Generic async block I/O trait. DONE 2026-05-19.** `AsyncBlockDevice`
   with AHCI callers migrated (Phase A, `04232c0`), USB MSC migrated and
   BPC dispatch collapsed (Phase B, `35ad890`). AHCI NCQ submit/complete
   split with an IRQ-driven dispatcher (Phase C1, `cf7938e`, fixed in
   `83a5117`), async readahead via lazy finalization by the first joiner
   (Phase C2, `83ddde9`), NCQ watchdog kthread (`22727bc`) and its
   counters in `/proc/ahci_stats` (`c5455d1`).

#1-#6 are all shipped. The foundations roadmap is closed.

Residual from #6, now closed: a port restart could leave pending the very
op it meant to fail. `fail_all_ncq_slots` skips a slot whose `issued` is
still false, and `reset_generation` was bumped at the *end* of
`restart_port`, after that pass; a submitter that stored `issued` in
between and sampled `SACT` before the reset cleared it saw an unchanged
generation and a set bit, so it returned and waited for a completion
nobody would deliver. The next watchdog sweep found it up to 30s later.

The gate this entry used to propose is not what fixes that. Gating
`enter_ncq_mode` on `restarting` keeps *new* submitters out; the one that
strands is already past the gate when the reset begins. The fix is
ordering: publish the generation before the fail-all pass, and have the
submitter re-read it after storing `issued`, so the two cover each other.
The gate went in anyway, as a throughput measure.

Validated rather than argued, since it touches the storage submit path.
`ahci_ncq_timeout_ms=0` on the kernel command line makes the watchdog
treat every in-flight op as hung, which is the only way to land resets
inside submits at any useful rate — a real NCQ command against a backing
file completes in well under a millisecond, so no sane positive timeout is
ever reached. `/proc/ahci_stats` gained `stranded`, counting ops a sweep
finds still pending from an earlier generation, which is the bug's exact
fingerprint. Under forced restarts with mixed read/write load: 1 stranded
in 33 restarts before the fix, 0 in 106 after.

Note: the `.claude/plans/*.md` and `.claude/handoff/*.md` paths cited
throughout this file are gone — that directory is not in the repo.
Treat the prose here as the record, not those links.

### Extend lock-order ranks to more subsystems (Foundation #4 follow-up)

Foundation #4 shipped rank instrumentation across VFS, page-cache,
journal, EFS, AHCI, frame allocator, and memory manager. The mechanism
(`ranked_lock!` + `Thread.lock_ranks` + per-thread rank stack) is
generic and applies to any `Mutex`/`RwLock`/`IrqSpinlock` in the
kernel. In the fs/mm audit it caught 3 real pre-existing inversions in
its first boot cycle (journal `tracker->state`, thread teardown
`mm->vmas`, EFS `mutable->BPC`). Extending to other subsystems is a
high-ROI way to shake out latent inversions before they manifest as
rare concurrent-load hangs. Candidates, ranked by fun-per-effort:

1. **Networking stack — DONE 2026-08-09.** Ranked `NET_STACK` 240,
   `PORT_TABLE` 250, `Socket` 260, `TcpConnection` 270, in the order the
   receive path fixes. Yield: two pre-existing AB/BA inversions, both
   taking the port table while holding something that belongs inside it
   (`tcp_retransmit_main` cleanup under a connection guard, and
   `close_descriptor` under a socket guard). Both sat between a syscall
   and a driver kthread that run concurrently, and neither is visible by
   reading either function alone. Details in
   `doc/invariants/lock-order.md`. Route table and ARP cache live inside
   `NetStack` and need no separate rank.
2. **USB stack — DONE 2026-08-10.** No locks to rank inside it: the
   `XhciController` is reached only as `&mut self` from its driver
   thread, and every other thread goes through a channel. The ranks the
   sweep added are the channels themselves — `Mailbox.queue` 204 and
   `ResponseInner.value` 206 (USB block I/O and FS mount requests),
   `Broadcaster.subs` 310, and the `/dev/kbd` + `/dev/mouse` poller
   lists 320. No inversions. Two real fixes came out of it:
   `Broadcaster.subs` was a bare `spin::RwLock` shared between kthreads
   and syscall context (now `PreemptRwLock`, and `subscribe` allocates
   its 256-slot queue before taking the guard), and the USB HID paths
   broadcast without notifying pollers, so `poll()` on `/dev/kbd` and
   `/dev/mouse` never fired with a USB device attached. Details in
   `doc/invariants/lock-order.md`.
3. **Window system — DONE 2026-08-09.** Ranked `WINDOW_REGISTRY` 280,
   `WINDOW_EVENTS` 290, `LAST_MOUSE_BUTTONS` 300. No inversions found:
   the registry is strictly outside, the input thread already drops its
   read guard before taking the write lock on a focus change, and
   nothing on the event-queue side reaches back into the registry. The
   read path is ranked inside `read_tracked`, which is the only way the
   registry is read, so every read site is covered by one call.
   `SHARED_MEMORY_REGISTRY` was left unranked here and got its rank from
   an mm-side analysis on 2026-08-10: rank 90, inside both address-space
   locks. The reason it could not be guessed from the window side is that
   the earlier "never co-held with vmas or mm" reading was wrong — it
   audited `syscalls/shm.rs` alone and missed `sys_fork`'s deep copy
   (under vmas 70) and `release_mappings` (under mm 80).
4. **HDA audio — DONE 2026-08-10.** One lock, not three: the whole
   driver (controller registers, BDL ring cursors, stream flag) sits
   behind `HdaPlaybackState`, rank 330. It was a bare `spin::Mutex`
   held across a memcpy loop into the DMA ring, shared between
   `/dev/dsp` writers and the HDA kthread; now a `PreemptSpinlock`.
   No inversions.
5. **devfs / PTY — DONE 2026-08-10.** `DevFs.shared` is rank 340,
   deliberately above every device lock it dispatches to, so a guard
   held across a driver callback panics instead of passing quietly.
   That caught a real one on the first `ls /dev`: `list_files` and
   `file_info` called `DeviceNode::file_entry` under the registry read
   guard, and `file_entry` reads `DevFsDevice::size`, which for
   `/dev/tty0` takes the rank-210 `BlockingMutex` — a spin lock held
   across a lock that can park. Both snapshot the nodes and build their
   entries after releasing the guard now. `TTY_POLLERS` also joined the
   device-poller class at 320 alongside the mouse and keyboard lists.

With that the list is finished; see "Every subsystem on the list is
ranked now" in `doc/invariants/lock-order.md`.

Marginal cost per subsystem: one rank constant, one row in
`doc/invariants/lock-order.md`, and s/`.lock()`/`.lock_ranked(RANK,
"site")`/ on ~10-30 sites. Per-subsystem cost a few hours; expected
payoff is a real bug or two per subsystem based on fs audit yield.

### GPU driver work (far future, no near-term plan)

The virtio-gpu driver we have is 2D only: dirty-rect transfers, blob
resources, hardware cursor. Two directions exist, and they teach
opposite halves of what a real GPU driver is. Neither is scheduled;
this is here so the options are written down rather than rediscovered.

**`ati-vga`, the hardware-facing half.** QEMU emulates a real ATI Rage
128 Pro / Radeon 9250 (`-device ati-vga,model=...`), with real MMIO
registers, a real 2D engine and a hardware cursor. The r100/r200
register documentation is public; it is what the classic `radeon` DRM
driver was built from. Bring-up would be authentic: PCI BAR probing,
MMIO programming, VRAM aperture setup, engine init, 2D blits, DMA.

The advantage over real silicon is that the device model *is* the spec.
`hw/display/ati.c` and `ati_2d.c` in the QEMU tree say exactly which
registers are implemented and what each does, so a hang is diffed
against the model rather than guessed at, and a `printf` can be added to
the model itself. The catch: it is hardware from 2003. No shaders, no
command processor, no GPU MMU.

**virtio-gpu 3D, the API-facing half.** Extending our existing
virtio-gpu driver past 2D means contexts, resource create/attach,
command-stream submission and fences, which is genuinely the object
model every modern DRM driver uses, and it builds on code we already
have.

Target the modern capsets rather than virgl. **Venus** (Vulkan) and
**native contexts** run a real Mesa driver in the guest and forward
actual hardware ioctls over the transport, so the guest side is doing
what a real driver does. Virgl is the older path: its command stream is
essentially serialised GL calls the host translates, which is further
from hardware and is not where the ecosystem went. QEMU exposes 3D
through the `-gl` device variants (`virtio-gpu-gl`, `virtio-vga-gl`),
which are compiled into the QEMU we run; the capset chosen on top of
that is what decides whether this is virgl or venus.

What the virtio path does *not* teach, and this is most of the
difficulty in a real driver: shader compilation to a hardware ISA, the
GPU's own MMU and page tables, firmware loading, engine scheduling and
preemption, clock and power management, and the VRAM/GTT hierarchy with
migration and eviction. Those live on the `ati-vga` side of the fence,
or on real silicon.

**Passthrough is not currently an option on the dev box.** VFIO would
need IOMMU enabled in firmware and on the kernel cmdline
(`/sys/kernel/iommu_groups` is empty today), and the only GPU is a
GeForce GT 710 driving the host display. A from-scratch Kepler driver
also means signed firmware for several engines; nouveau still cannot
reclock Kepler properly.
