
- FIXED: attaching a USB mass-storage device hung the boot.
  `xhci_driver_main` called `crate::fs::api::register_partition` inline, between
  `xhci: initial enumeration complete` and the mailbox drain in its event loop.
  Registration makes the fs kthread scan the new device for a partition table,
  and `UsbBlockDevice::submit_read` posts those reads to `USB_BLOCK_MAILBOX` --
  which only the xHCI thread drains. The two threads deadlocked: measured with
  `log!` on both sides, the wake was delivered at t=1.687 to a thread whose
  first loop iteration was at t=21.71, i.e. only after the fs kthread's second
  10s timeout expired. Fix: registration is posted to a `usb-register` kthread
  so `xhci_driver_main` falls straight into its loop. Verified with
  `scripts/edos-vm start --usb-disk`: `fs: registered partition: USB Storage 0`
  at t=1.691 and `[Terminal] Spawned shell`.
  The fs side is also no longer unbounded: `send_and_wait` uses
  `Response::wait_timeout(10s)` and fails the read with `BlockError::Timeout`.

- Intermittent segfault in fsbench's `mmap store 4MiB + msync`, recorded at
  ~1 run in 6 on 2026-08-09, NOT reproduced since: 37 suite runs across 4 and
  8 vCPUs on a freshly formatted disk, all clean. The KILL line now names why
  the fault handler declined (FaultReject), so the next occurrence should be
  self-diagnosing rather than needing another bisect. Check the `reject=` field
  first: PastEof means a size shrank under the mapping, FillFailed means the
  block map lost the page, NoVma means the mapping itself went away.

- edos_lib duplicates edos_rt's syscall wrappers and SYS_* constants. Since
  edos_rt 0.0.37 dropped no_mangle from them, a program can depend on the
  crate directly, so the two lists could become one. Reconciling two sets of
  syscall numbers is where a silent wrong-number bug would come from, so it
  wants doing deliberately rather than as a drive-by.

- SYS_OPEN takes a NUL-terminated path while SYS_STAT takes pointer+length.
  edos_rt no longer pays for it (FileDesc::new goes through SYS_OPENAT with
  AT_FDCWD, which needs no CString), but edos_lib and every program that calls
  it still use the NUL-terminated forms, and the kernel still carries both.
  Settling on pointer+length everywhere changes the ABI and every caller.


- `make test AUDIODEV=none` intermittently fails on the ping-pong pair, and the
  immediate re-run of the same ISO passes 49/49. Two signatures so far, both on
  2026-08-10:
    * "[sched-test] ping-pong count mismatch: 499 != 500", TIMEOUT at 47/49.
    * TIMEOUT at 48/49 with no FAIL line at all: `ping-pong-ping` passed and
      `ping-pong-pong` never reported, so the pong thread was still parked when
      the 10s deadline fired.
  Both point at a lost or late wakeup on the pong side rather than at the
  counter. Catch the failing run's full log before chasing it; the counter and
  the missing PASS line are the only evidence printed today.


- fg resumes a job but /proc still shows the process Stopped afterwards.
  Repro: cat, Ctrl+Z, fg, then ps. SIGCONT clears the flag at delivery now,
  so something re-sets it or the target re-enters the park.
- A stop or kill signal does not cut short sys_sleep_ms, so Ctrl+Z on
  `sleep 30` only takes effect 30s later. thread_sleep should return early
  when stop_requested or killed is set.

- There is no `/dev/null`. `yes > /dev/null` fails with "cannot open for
  writing", so the standard way to discard output does not exist and every
  script that wants it has to write to a file under /tmp. One more node in the
  devfs registry (`kernel/src/fs/devfs`), reads returning EOF and writes
  succeeding with the byte count. `/dev/zero` and `/dev/full` are the same
  shape and worth adding in the same change.

- The terminal does not implement DECTCEM: `\x1b[?25l` / `\x1b[?25h` are
  ignored, so `top` and `snake` cannot hide the cursor. `parse_csi_params` in
  edos_render/src/widgets/terminal.rs drops the `?` (parse::<usize>() -> 0)
  and `l`/`h` have no arm in execute_csi. Needs a private-parameter flag on the
  CSI state plus the two arms.

- The TCP accept queue never drops an entry that never reached Connected.
  kernel/src/net/stack.rs pushes a new Socket onto listen_sock.accept_queue on
  every SYN, and sys_accept only removes entries whose state is Connected, so a
  half-open connection (a SYN whose SYN-ACK was dropped, e.g. on an ARP miss,
  and every retransmit of it) occupies a backlog slot forever. Symptom seen with
  `tcpecho -p 23`: after a timed-out first connection plus two good ones, the
  next SYN gets no SynReceived line at all and the peer sees RST — the backlog
  of 4 is full of dead entries. Wants a SynReceived timeout, or a cap on
  half-open entries separate from the completed-connection backlog.
- An outbound segment is dropped when the ARP cache misses (send_ip returns
  Err("arp pending"), kernel/src/net/stack.rs) and nothing retries it, so the
  first inbound connection after boot is lost: the SYN-ACK never goes out. A
  one-slot pending-transmit queue per ARP request would fix it.
