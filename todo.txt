
- Attaching a USB mass-storage device HANGS THE BOOT, reproduced deterministically
  with `scripts/edos-vm start --usb-disk` (the same machine without the flag
  reaches `[Term] FocusGained`). Enumeration is fine and the identity is correct,
  so nothing before the first bulk read is at fault:
    xhci: USB storage: vendor='QEMU' product='QEMU HARDDISK'
    xhci: USB storage: 32768 blocks x 512 bytes = 16 MiB
    usb-msc: registered /dev/usb0
  The last line ever printed is `reading sector for gpt` (`fs/gpt.rs:248`), so
  the `fs` kthread blocks inside `read_sectors_vec(usb0, lba 1, 1)` and never
  reaches the `read gpt sector` line after it.
  The fs kthread never touches the device itself: `UsbBlockDevice::submit_read`
  (`drivers/usb/block_dev.rs:59`) hands the request to `USB_BLOCK_MAILBOX`,
  wakes the xHCI thread, and blocks in `Response::wait`. Only the xHCI thread
  ever calls `bot_transfer`, and that call is already bounded — `bulk_transfer`
  (`drivers/usb/xhci/mod.rs:1029`) polls at most 10M times and then returns
  `CommandTimeout` — so a deadline in `bot_transfer` is NOT the fix and would
  not have unwedged this boot. The stall is in the mailbox round trip: either
  the request is never picked up or the reply is never posted.
  What the boot log rules in and out, in order:
    - the xHCI thread reached the main loop (`xhci: initial enumeration
      complete`, run_log line 121) and printed nothing afterwards, so it is
      parked in the `thread_park_while` at `xhci/mod.rs:1469` and never
      re-entered the mailbox drain at `:1618`.
    - the park predicate re-checks `!mb.is_empty()` under `try_lock`, and a
      contended lock reads as non-empty, so a lost wake from the predicate
      racing `Mailbox::send` is ruled out. What is left is the wake itself:
      `send_and_wait` calls `sched().wake_thread(XHCI_DRIVER_THREAD_ID, ...)`,
      and the thread is idle with no HID traffic in a headless guest, so that
      wake is the *only* thing that can run it. If it lands while the thread is
      mid-transition into the park, nothing else ever arrives to retry it.
    - the `<cpu-1:kernel>` tag on every xHCI line says NOTHING about which
      thread ran them: the whole driver logs with `println!`, and
      `serial::_serial_print` (`serial.rs:45`) hardcodes that prefix. Only
      `log!` consults `current_thread()`. So the xHCI thread's identity is
      still unobserved, and there is no evidence it is the wrong thread.
    - the waiter is a real kthread and not a self-deadlock: the hanging
      `reading sector for gpt` is tagged `<cpu-2:fs:k:14>` (run_log line 241),
      from `log!`, so the fs kthread — not the xHCI thread — is the one
      blocked in `Response::wait`. The gpt scan on the previous device
      (lines 231-232) completed on that same thread.
    - the wake is not a silent no-op either: `drivers::init` calls
      `usb::init()` (`drivers/mod.rs:95`), which `call_once`s
      `XHCI_DRIVER_THREAD_ID` before any filesystem is mounted, so
      `send_and_wait`'s `if let Some(handle)` is taken.
    What is left is the wake itself against a thread parked in
    `thread_park_while`. The next experiment needs `log!` (never `println!`)
    on both sides: one line where the park returns in `xhci_driver_main`
    (`xhci/mod.rs:1475`) reporting `current_thread_id()`, and one in
    `send_and_wait` after `wake_thread` reporting the target's id and the
    value `wake_thread` returned. That shows whether the wake reached a
    thread that then failed to re-enter the drain, or never landed at all.
  Give the fs side a deadline regardless: `Response::wait` blocks forever, so a
  wedged or unwoken driver thread wedges the boot instead of failing the read.

- The AHCI ATAPI commands read a fixed number of bytes out of a pooled DMA
  buffer without asking how many arrived, the same defect fixed in 7591982
  (xHCI descriptors) and in the USB mass-storage INQUIRY / READ CAPACITY
  paths. `execute_atapi_command` (`kernel/src/drivers/ahci/port.rs:1941`)
  returns `Result<(), _>` and drops the count, so
  `execute_atapi_inquiry_as_identify` parses all 96 bytes,
  `execute_atapi_read_capacity` all 8, and `execute_atapi_read_as_sectors`
  copies the whole `expected_size` back to the caller. `DmaPool` does not zero
  a recycled buffer, so a short response yields the previous owner's bytes as
  device identity or as sector data.
  The count is already available: `issue_command` zeroes the command header's
  `prdbc` before issuing (`port.rs:1026`) and the HBA writes the transferred
  byte count there on completion, so `execute_atapi_command` can read it back
  after `wait_for_completion` and return it. Not done tonight because nothing
  in the current QEMU setup exercises an ATAPI device, so gating those reads on
  `prdbc` would ship an unverified behaviour change on the storage path.

- An absolute symlink target is resolved in the wrong namespace. Root cause of
  `iotest /tmp` failing test 10 with "read through link: entity not found"
  while the identical `iotest /var` passes: VFS hands each filesystem a
  MOUNT-RELATIVE path, and each filesystem resolves link targets from its own
  root. `splice_symlink` discards the prefix for a target starting with `/`, so
  a link at /tmp/link naming "/tmp/target" makes memfs look for `tmp/target`
  under the memfs root, which has no `tmp`. EFS only works because it is
  mounted at `/`, where mount-relative and absolute coincide. Relative targets
  are unaffected on both.
  The fix belongs in the VFS, which is the only layer that owns the namespace:
  a filesystem must not follow an absolute target at all, and VFS must restart
  resolution from the VFS root, crossing mounts, capped at MAX_SYMLINK_HOPS.
  What makes it more than a one-liner: the follow/nofollow distinction
  currently lives inside each filesystem's walk, so `read_link`, `remove_file`
  and `symlink` (vfs.rs:952-1005) need a resolve entry point that leaves the
  final component alone while every other op gets one that follows it, and the
  followed path can land on a different mount than the one the link lives on,
  so `VfsOp.fs` has to come from the target. Doing it by probing each path
  prefix with `read_link` is the obvious shape and is O(N) fs walks per
  lookup — too slow for `resolve()`; escalating only when the filesystem
  reports it hit an absolute target keeps the fast path free.

- Intermittent segfault in fsbench's `mmap store 4MiB + msync`, recorded at
  ~1 run in 6 on 2026-08-09, NOT reproduced since: 37 suite runs across 4 and
  8 vCPUs on a freshly formatted disk, all clean. The KILL line now names why
  the fault handler declined (FaultReject), so the next occurrence should be
  self-diagnosing rather than needing another bisect. Check the `reject=` field
  first: PastEof means a size shrank under the mapping, FillFailed means the
  block map lost the page, NoVma means the mapping itself went away.

- edos_lib duplicates edos_rt's syscall wrappers and SYS_* constants. Since
  edos_rt 0.0.37 dropped no_mangle from them, a program can depend on the
  crate directly, so the two lists could become one. Reconciling two sets of
  syscall numbers is where a silent wrong-number bug would come from, so it
  wants doing deliberately rather than as a drive-by.

- SYS_OPEN takes a NUL-terminated path while SYS_STAT takes pointer+length,
  so edos_rt allocates a CString for every open. Settling on pointer+length
  everywhere removes that allocation but changes the kernel ABI and every
  caller.

- `std::thread::sleep` still rounds every request down to whole milliseconds:
  the fork's `sys/thread/edos.rs` calls `edos_rt::process::sleep_ms`, so a
  sub-millisecond sleep returns immediately. SYS_NANOSLEEP (35) now exists and
  `edos_lib::time::nanosleep` reaches it; pointing std at it needs an edos_rt
  release and a fork pin bump.
