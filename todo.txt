- The heap VMA is created with PROT_WRITE and no PROT_READ: `pmap` on any
  process shows the `brk` region as `-w-p` while every other mapping is `r--`
  or `rw-`. x86 has no write-without-read encoding so nothing breaks, but the
  VMA record is wrong and a future `mprotect` or a permission check that
  believes it would reject a legitimate read. Look at where `heap_break` grows
  a VMA in `kernel/src/syscalls/memory.rs`.
- `/proc/<tid>/maps` names a file-backed mapping `file:<mount>:<ino>` because a
  `VfsInode` carries no path and the dentry that named it may be gone. A path
  would need a reverse lookup through the dentry cache, or the mapping to
  remember the path it was opened with.



- FIXED: attaching a USB mass-storage device hung the boot.
  `xhci_driver_main` called `crate::fs::api::register_partition` inline, between
  `xhci: initial enumeration complete` and the mailbox drain in its event loop.
  Registration makes the fs kthread scan the new device for a partition table,
  and `UsbBlockDevice::submit_read` posts those reads to `USB_BLOCK_MAILBOX` --
  which only the xHCI thread drains. The two threads deadlocked: measured with
  `log!` on both sides, the wake was delivered at t=1.687 to a thread whose
  first loop iteration was at t=21.71, i.e. only after the fs kthread's second
  10s timeout expired. Fix: registration is posted to a `usb-register` kthread
  so `xhci_driver_main` falls straight into its loop. Verified with
  `scripts/edos-vm start --usb-disk`: `fs: registered partition: USB Storage 0`
  at t=1.691 and `[Terminal] Spawned shell`.
  The fs side is also no longer unbounded: `send_and_wait` uses
  `Response::wait_timeout(10s)` and fails the read with `BlockError::Timeout`.

- Intermittent segfault in fsbench's `mmap store 4MiB + msync`, recorded at
  ~1 run in 6 on 2026-08-09, NOT reproduced since: 37 suite runs across 4 and
  8 vCPUs on a freshly formatted disk, all clean. The KILL line now names why
  the fault handler declined (FaultReject), so the next occurrence should be
  self-diagnosing rather than needing another bisect. Check the `reject=` field
  first: PastEof means a size shrank under the mapping, FillFailed means the
  block map lost the page, NoVma means the mapping itself went away.

- users, file perms. `stat` reports the read-only bit in `FstatEntry::attrs`
  and `Metadata::permissions().readonly()` now answers from it, but nothing

  `fs::set_permissions` reports Unsupported. Wants a `FileSystem::set_attrs`

- direct copy file (rename exists as SYS_RENAME; a copy that stays in the kernel
  does not, so `cp` reads and writes through userspace)

- edos_lib duplicates edos_rt's syscall wrappers and SYS_* constants. Since
  edos_rt 0.0.37 dropped no_mangle from them, a program can depend on the
  crate directly, so the two lists could become one. Reconciling two sets of
  syscall numbers is where a silent wrong-number bug would come from, so it
  wants doing deliberately rather than as a drive-by.

- SYS_OPEN takes a NUL-terminated path while SYS_STAT takes pointer+length.
  edos_rt no longer pays for it (FileDesc::new goes through SYS_OPENAT with
  AT_FDCWD, which needs no CString), but edos_lib and every program that calls
  it still use the NUL-terminated forms, and the kernel still carries both.
  Settling on pointer+length everywhere changes the ABI and every caller.

- fg resumes a job but /proc still shows the process Stopped afterwards.
  Repro: cat, Ctrl+Z, fg, then ps. SIGCONT clears the flag at delivery now,
  so something re-sets it or the target re-enters the park.
  Ruled out: `stop_if_signalled` is not the leak. It stores `stopped = false`
  unconditionally on the way out of its park, so a thread that resumes at all
  clears the flag. Either the SIGCONT wake is lost and the thread never leaves
  the park (which contradicts the job visibly resuming), or something drives it
  back through `stop_if_signalled` after the resume. Instrument which of the two
  boundaries -- the syscall return or the ring-3 tick -- re-enters it.
- A stop or kill signal does not cut short sys_sleep_ms, so Ctrl+Z on
  `sleep 30` only takes effect 30s later. thread_sleep should return early
  when stop_requested or killed is set.

- The terminal does not implement DECTCEM: `\x1b[?25l` / `\x1b[?25h` are
  ignored, so `top` and `snake` cannot hide the cursor. `parse_csi_params` in
  edos_render/src/widgets/terminal.rs drops the `?` (parse::<usize>() -> 0)
  and `l`/`h` have no arm in execute_csi. Needs a private-parameter flag on the
  CSI state plus the two arms.

- The TCP accept queue still has no timeout on an entry that never reaches
  Connected. Visible now: `netstat -a` in the guest lists the stranded entry as
  `SYN_RECV` with one unacknowledged byte, and it never leaves the list.
  A retransmitted SYN no longer multiplies them — the SYN path in
  kernel/src/net/stack.rs now drops the half-open entry left by the same peer
  address and port before starting the handshake again — but a peer that opens
  one connection and vanishes still holds its backlog slot until the listener
  closes. Wants a SynReceived deadline, or a half-open cap separate from the
  completed-connection backlog.
- An outbound segment is dropped when the ARP cache misses (send_ip returns
  Err("arp pending"), kernel/src/net/stack.rs) and nothing retries it, so the
  first inbound connection after boot is lost: the SYN-ACK never goes out.
  `netstat -a` shows the casualty as a `SYN_RECV` row with Send-Q 1. A
  one-slot pending-transmit queue per ARP request would fix it.

- A process's arguments are not recorded anywhere, so nothing in userspace can
  show them. `/proc/<pid>/cmdline` looks like the file that would carry them,
  but `ThreadSnapshot::cmdline_text` in kernel/src/fs/procfs/mod.rs just prints
  the thread name, and the name is the path `exec` was given, without argv.
  `sleep 60` and `sleep 1` are indistinguishable in `ps`, `top` and `pstree`.
  Wants argv retained on the Thread (a joined String is enough) at
  load_process_image time, and cmdline_text rendering it. `pstree` has `-l` for
  the full path instead, which is all the kernel can answer today.

- Context switch cost, the top item for the next round, now measured rather
  than guessed. `switchbench` on a single-CPU boot and `/proc/sched_prof`
  (`--features sched-prof`) put one switch at 1270 ns, of which:
  - **`set_apic_timer` is 1024 ns**, 81% of the whole switch. One x2APIC write
    to `IA32_TSC_TMICT`, trapped by KVM, done on every switch to push the
    incoming thread's timeslice deadline out. Nothing else is close.
  - `FS.base` costs 104 ns as `RDMSR` + `WRMSR`, while `CR4.FSGSBASE` has been
    on since boot and `rdfsbase`/`wrfsbase` cost a cycle or two.
  - `fxsave` + `fxrstor` is 93 ns. Unconditional and 512 bytes wide whether or
    not the thread touched the FPU; `XSAVEOPT` with a dirty check is the fix,
    and it decides what the save area has to hold, so pair it with the
    `-cpu host` question.
  - `switch_to_page` is 67 ns, and a cross-process handover costs ~380 ns more
    than a same-address-space one, so PCID is worth roughly that much plus the
    refill misses that land after the switch.
  - The `CpuContext` copies under a spin `Mutex` are 40 ns for both sides
    together. Not worth restructuring on their own.
  The two-thread ping-pong the last round asked for has been run, and it
  cleared the doubt rather than confirming it: a real handover costs the same
  as a self-yield within noise, so the idle figure was never hiding anything.
