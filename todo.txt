
- `BitmapFrameAllocator::inc_or_set_refcount` documents itself as being used by
  `map_address` / `map_address_range`, and nothing calls it. `map_address`
  instead calls `set_frame_allocated`, which leaves the refcount at 0 — the
  allocator's "reserved, never hand this out" state. Either wire it up or
  correct the doc; a doc naming a caller that does not exist is the trap that
  hid the ACPI teardown bug.

- An absolute symlink target is resolved in the wrong namespace. Root cause of
  `iotest /tmp` failing test 10 with "read through link: entity not found"
  while the identical `iotest /var` passes: VFS hands each filesystem a
  MOUNT-RELATIVE path, and each filesystem resolves link targets from its own
  root. `splice_symlink` discards the prefix for a target starting with `/`, so
  a link at /tmp/link naming "/tmp/target" makes memfs look for `tmp/target`
  under the memfs root, which has no `tmp`. EFS only works because it is
  mounted at `/`, where mount-relative and absolute coincide. Relative targets
  are unaffected on both.
  The fix belongs in the VFS, which is the only layer that owns the namespace:
  a filesystem must not follow an absolute target at all, and VFS must restart
  resolution from the VFS root, crossing mounts, capped at MAX_SYMLINK_HOPS.
  What makes it more than a one-liner: the follow/nofollow distinction
  currently lives inside each filesystem's walk, so `read_link`, `remove_file`
  and `symlink` (vfs.rs:952-1005) need a resolve entry point that leaves the
  final component alone while every other op gets one that follows it, and the
  followed path can land on a different mount than the one the link lives on,
  so `VfsOp.fs` has to come from the target. Doing it by probing each path
  prefix with `read_link` is the obvious shape and is O(N) fs walks per
  lookup — too slow for `resolve()`; escalating only when the filesystem
  reports it hit an absolute target keeps the fast path free.

- edos_lib duplicates edos_rt's syscall wrappers and SYS_* constants. Since
  edos_rt 0.0.37 dropped no_mangle from them, a program can depend on the
  crate directly, so the two lists could become one. Reconciling two sets of
  syscall numbers is where a silent wrong-number bug would come from, so it
  wants doing deliberately rather than as a drive-by.

- mkdir on an existing directory reports EIO, so std shows "other error" where
  it should be AlreadyExists. The kernel's From<FsError> for Errno has no
  EEXIST source: fs::Error has no AlreadyExists variant, so create_file and
  mkdir cannot distinguish it. Now visible because userspace keeps the errno.

- SYS_OPEN takes a NUL-terminated path while SYS_STAT takes pointer+length,
  so edos_rt allocates a CString for every open. Settling on pointer+length
  everywhere removes that allocation but changes the kernel ABI and every
  caller.

- memfs reads past EOF, returning zeros to the end of the last page. `stat` on
  /tmp/hello.txt says 20 bytes and `cat` prints the right text, but sha256sum
  hashes 4096 bytes and hexdump dumps to the page boundary, so a guest checksum
  of a file on /tmp never matches the host's. The same file on /var (EFS) hashes
  correctly, and /bin/true matches the host exactly.
  RE-VERIFY BEFORE CHASING: the mechanism originally written here (VFS read()'s
  file_size_ino clamp not reaching memfs) is contradicted by the code. memfs has
  implemented PageCacheOps since ddfb50a, its file_size_ino returns
  node.content.len(), and vfs::read clamps count to it before page_cache_read.
  Suspect the write path inflating node.content to a page boundary instead, and
  confirm the symptom still reproduces before touching the read path.

- `std::thread::sleep` still rounds every request down to whole milliseconds:
  the fork's `sys/thread/edos.rs` calls `edos_rt::process::sleep_ms`, so a
  sub-millisecond sleep returns immediately. SYS_NANOSLEEP (35) now exists and
  `edos_lib::time::nanosleep` reaches it; pointing std at it needs an edos_rt
  release and a fork pin bump.
