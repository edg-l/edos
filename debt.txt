# Technical Debt

## Mouse/GUI deadlock on mouse movement (pre-existing)

Moving the mouse can freeze the WM/GUI. The mouse driver thread runs
process_packet -> MOUSE_BROADCAST.broadcast(event) which calls
wake_thread(sub.owner) for each subscriber. The broadcast holds
subs.read() (spin RwLock) while waking threads. Meanwhile the mouse
interrupt can fire on the same CPU calling wake_thread_irq for the
mouse driver thread itself.

Possible causes:
- Broadcaster subs RwLock contention between broadcast() and cleanup()
- BlockingMutex in MOUSE_POLLERS taken during notify_mouse_pollers()
  while the mouse interrupt tries to wake the driver thread
- wake_thread_slow spinning while holding/waiting for locks that the
  woken thread needs

Needs investigation with GDB (make run-gdb) to capture the actual
deadlock state and identify which locks are contended.

## Per-CPU scheduler stack — DONE

Implemented in scheduler::init() (stack allocation) and
save_transition_switch (RSP pivot after do_save_current_thread).
complete_wake now enqueues on the waker's CPU for cache locality.
